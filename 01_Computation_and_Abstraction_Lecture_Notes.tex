\section{Computation as a Mechanical Process}

\subsection{A motivating problem}

Consider the decision problem
\[
  \text{Is }35{,}500{,}001\text{ divisible by }113?
\]
Long division gives
\[
  35{,}500{,}001=113\times314{,}159+34.
\]
The remainder is $34$, so the answer is \emph{no}.

The familiar long-division procedure consists of a small collection of steps:
\begin{enumerate}
  \item divide or estimate the next quotient digit;
  \item multiply the divisor by that digit;
  \item subtract;
  \item bring down the next input digit;
  \item repeat until no input remains.
\end{enumerate}
Nothing in these steps requires a new creative insight once the procedure has been specified. A person or a machine can follow the same rules. This repeatable, rule-governed character is the first sense in which computation is \emph{mechanical}.

In treating long division as a mechanical process, we assume that its elementary
operations---such as short division, single-digit multiplication, subtraction,
comparison, and bringing down the next digit---can themselves be carried out
mechanically. We call these primitive operations \emph{instructions}; the finite
collection of instructions available to a machine is its \emph{instruction set}.
At this level of abstraction, we specify what each instruction does without yet
explaining how the machine implements it.

The implementation of such instructions is studied at lower levels of computer
systems. Relevant topics and courses include Boolean algebra and switching
theory, digital logic design, combinational and sequential circuits, arithmetic
circuits such as adders and multipliers, computer organization and architecture,
instruction-set architecture, and processor microarchitecture. These subjects
show how elementary mechanical steps can ultimately be realized using logic
gates, registers, data paths, and control circuits.

\subsection{Algorithm, input, and output}

\begin{definition}[Algorithm]
An \emph{algorithm} is a finite, unambiguous sequence of instructions for solving a class of problems. It specifies how to transform an input into an output.
\end{definition}

For the divisibility example, an input may consist of a dividend $a$ and a
divisor $b$. Although our numerical example is small enough to write on one
line, computer science studies the entire family of possible inputs rather than
only this one instance. The dividend may be extremely long---possibly millions
or billions of digits---so an algorithm must describe a uniform procedure that
works regardless of the particular input length. If the dividend has $n$ digits,
we treat $n$ as its input size and ask how the algorithm's time and memory usage
grow as $n$ increases. The requested output then determines the type of problem:

\begin{center}
\begin{tabularx}{0.92\linewidth}{>{\bfseries}p{0.23\linewidth}X p{0.27\linewidth}}
\toprule
Problem type & Required output & Example \\
\midrule
Decision & yes or no & Is $a$ divisible by $b$? \\
Search & a particular object or value & What is the remainder of $a/b$? \\
Counting & the number of valid objects & How many divisors does $a$ have? \\
Optimization & the best feasible object or value & Which valid solution has minimum cost? \\
\bottomrule
\end{tabularx}
\end{center}

A search problem asks us to produce a particular object, often called a
\emph{solution} or \emph{witness}, that satisfies specified conditions. For many
important search problems, if we are given a candidate solution, we can verify
efficiently that it is correct, even though finding such a solution may be much
harder. This distinction between finding and verifying a solution will become
important when we discuss the complexity class NP.

The output $34$ solves the remainder-search problem. The output \emph{no} solves
the original decision problem.

\subsection{Correctness and efficiency}

The same function can have several algorithms. Repeatedly subtracting $113$ from $35{,}500{,}001$ will eventually produce the correct remainder, but it needs roughly $314{,}159$ subtractions. Long division processes the input one digit at a time and therefore requires a number of rounds proportional to the number of digits.

This example separates two questions:
\begin{itemize}
  \item \textbf{Computability:} Can any mechanical procedure solve the problem for every valid input?
  \item \textbf{Complexity:} How much time and memory does a particular procedure require as the input grows?
\end{itemize}

\section{From a Human Calculator to a Turing Machine}

When performing long division by hand, we use paper as memory, symbols for data, eyes to read, a hand and pencil to write, a finite collection of remembered instructions, and rules that determine the next action. Turing's model keeps only these essential components.

\subsection{The abstract machine}

A Turing machine has:
\begin{itemize}
  \item an unbounded one-dimensional tape divided into cells;
  \item a finite tape alphabet, including a blank symbol;
  \item a read/write head that scans one cell at a time;
  \item a finite set of control states, including a start state and one or more halting states;
  \item a transition function that determines the next action.
\end{itemize}

The transition function has the form
\[
  \delta(q,a)=(q',b,D),
\]
where $q$ is the current state, $a$ is the scanned symbol, $q'$ is the next state, $b$ is the symbol written to the tape, and $D\in\{L,R\}$ is the direction of movement.

\begin{figure}[htbp]
  \centering
  \includesvg[width=0.5\linewidth]{01 Figures/Turing Machine.svg}
  \caption{The basic components of a Turing machine.}
  \label{fig:turing-machine-components}
\end{figure}

\subsection{Why one-dimensional and unbounded?}

A sheet of paper is two-dimensional, but its cells can be enumerated and placed along a one-dimensional tape. This transformation simplifies the mechanism: the head needs only to move left or right. The precise enumeration is unimportant as long as it preserves all information.

The tape is \emph{unbounded} because the size of a valid input has no fixed upper limit. For any particular run, the machine uses only finitely many cells. If it needs more, the model permits more tape. This idealization separates computability from the accidental memory limit of a physical computer.

\begin{figure}[htbp]
  \centering
  \includesvg[width=0.5\linewidth]{01 Figures/2D to 1D.svg}
  \caption{Mapping a two-dimensional grid to a one-dimensional tape.}
  \label{fig:two-dimensional-to-one-dimensional-tape}
\end{figure}

\subsection{Finite-state control}

The machine has only \emph{finitely many} states. This resembles human mechanical
work: the brain keeps limited control information in mind, while details are
recorded externally on paper. In a Turing machine, the states provide limited
internal control and the tape provides external memory.

LEGO offers a similar analogy. There are finitely many types of pieces, yet
arbitrarily many copies can be combined to build models without a fixed size
limit. Likewise, a Turing machine reuses finitely many states and rules across
arbitrarily many tape cells.

Finite control is required for two reasons. First, a mechanical controller must
have a finite description and use limited physical resources. Second, infinitely
many states could store one answer for every possible input. The machine would
then be an infinite lookup table or enumeration, not an algorithm applying
reusable steps. Finite states prevent this shortcut and require genuine
computation by a finite set of rules.

\subsection{Unbounded execution and halting}

Unbounded execution means that the model imposes no fixed upper limit on the
number of steps a computation may take. It does not mean that every computation
runs forever. A particular run may halt after finitely many steps, but different
inputs may require increasingly many steps, and some runs may never halt.

Unbounded execution is different from unbounded memory. A machine can execute
forever using only a fixed amount of tape by repeatedly visiting the same cells
in a loop. Conversely, the unbounded tape means that no fixed memory limit is
imposed in advance, although only finitely many cells have been visited at any
finite point in a run. Time counts transitions; memory counts the tape cells used.

\begin{definition}[Halting]
A computation \emph{halts} when the machine reaches a designated halting state
or when no transition rule applies. This event is its \emph{halting condition}.
If the condition is never reached, the machine continues executing indefinitely.
\end{definition}

For algorithms computing a function, a correct algorithm must halt on every
input covered by its specification and produce the required output. Reactive
systems such as network services, by contrast, are specified to run
indefinitely; their correctness is defined by safety and liveness properties
rather than eventual termination.

\subsection{A Turing-machine view of long division}

Fix the divisor at $113$. A state can record the current remainder $r$, where $0\le r<113$. When the head reads the next decimal digit $d$, compute
\[
  t=10r+d,\qquad c=\left\lfloor\frac{t}{113}\right\rfloor,
  \qquad r'=t\bmod113.
\]
The machine writes the quotient digit $c$ to the tape, moves right, and changes
to the state representing $r'$. The remainder can be kept in the finite control
because it is always one of the $113$ values from $0$ to $112$. The quotient is
different: it can have nearly as many digits as the dividend and therefore has
no fixed maximum length. A finite set of states cannot store an arbitrarily long
quotient, so the machine must write its digits incrementally to the tape. For the
input $35500001$, the computation is:

\begin{center}
\small
\begin{tabular}{c@{\qquad}c@{\qquad}c}
\toprule
Digit read & Quotient prefix & Remainder state \\
\midrule
$3$ & $0$ & $3$ \\
$5$ & $00$ & $35$ \\
$5$ & $003$ & $16$ \\
$0$ & $0031$ & $47$ \\
$0$ & $00314$ & $18$ \\
$0$ & $003141$ & $67$ \\
$0$ & $0031415$ & $105$ \\
$1$ & $00314159$ & $34$ \\
\bottomrule
\end{tabular}
\end{center}

After the machine reaches the blank cell, it halts. The final non-leading-zero quotient is $314159$ and the remainder state is $34$.

\begin{keyidea}[What the model establishes]
The Turing machine is not a blueprint for a fast computer. It is a deliberately minimal mathematical model that makes the phrase ``mechanical procedure'' precise enough to study.
\end{keyidea}

\section{More Algorithms and More Machines}

\subsection{The Euclidean algorithm}

Another example problem is to find the \emph{greatest common divisor}: the largest
positive integer that divides both given integers without a remainder. In this
example, we want to find the greatest common divisor of $404$ and $96$, written
$\gcd(404,96)$.

To compute it, repeatedly replace the larger pair by the divisor and the remainder:
\begin{align*}
404 &= 4\cdot96+20,\\
 96 &= 4\cdot20+16,\\
 20 &= 1\cdot16+4,\\
 16 &= 4\cdot4+0.
\end{align*}
The last nonzero remainder is $4$, so $\gcd(404,96)=4$.

If $a$ and $b$ have many digits, finding the quotient and remainder in each
round is not a single elementary instruction: it can require long division.
Thus, Euclid's algorithm uses division as a subroutine. The number of rounds
and the work needed for each division are separate parts of its running cost.

Like long division, this procedure uses a fixed collection of operations and a
repeat rule. We can therefore design another Turing machine whose states
implement it.

  \centering

The Euclidean algorithm can be implemented directly as follows:
\begin{center}
\begin{minipage}{0.67\linewidth}
\begin{lstlisting}[language=Python]
def gcd(a, b):
    while b != 0:
        a, b = b, a % b
    return a
\end{lstlisting}
\end{minipage}
\end{center}

\subsection{The prime-factorization method}

Prime factorization provides another method for finding a greatest common
divisor. Factor each input into primes, retain every prime shared by both
factorizations, and use the smaller exponent when a shared prime occurs more
than once. For the same example,
\[
  404=2^2\cdot101,
  \qquad
  96=2^5\cdot3.
\]
The only shared prime is $2$, and the smaller exponent is $2$. Therefore,
\[
  \gcd(404,96)=2^2=4.
\]
This method computes the same GCD function as the Euclidean algorithm, but it
requires prime factorizations and therefore has a very different computational
cost.

\begin{conceptcheck}[Homework]
Our course code is $44{,}511{,}105$. Find its prime factorization.
\end{conceptcheck}

The homework is intended to make the cost of an algorithm tangible: finding
prime factors can take much more work than checking a proposed factor by
division. Testing whether a remaining large factor is prime is a separate
algorithmic task. For very large integers, the difficulty of finding factors
also motivates public-key cryptography, including RSA. This is a question of
\emph{efficiency}, not computability: factoring is possible by a mechanical
procedure even if a particular instance is hard to solve in practice.

\subsection{Functions versus algorithms}

\begin{definition}[Function and algorithm]
The \emph{problem specification} states what output is required for each valid
input. When every input has a unique output, this input--output relationship is
a \emph{function}; a search problem may instead permit several valid outputs.
An \emph{algorithm} is a particular sequence of instructions for computing an
output that satisfies the specification. Thus, a function specifies \emph{what}
must be computed, whereas an algorithm specifies \emph{how} to compute it.
Several different algorithms may compute the same function or solve the same
problem.
\end{definition}

For example, $\gcd(a,b)$ is a function. The Euclidean algorithm and a
factorization-based method are algorithms that compute it.

Integer multiplication is also a function. The schoolbook multiplication
algorithm for two $n$-digit integers uses $O(n^2)$ single-digit multiplications,
while faster multiplication algorithms compute the same function with a lower
asymptotic running time.

\section{The Universal Turing Machine}

Building a separate physical machine for every algorithm would be possible in principle but impractical. A universal Turing machine $U$ accepts both an encoded machine $\langle M\rangle$ and an input $x$:
\[
  U(\langle M\rangle,x)=M(x).
\]
It reads the description of $M$ and simulates $M$ step by step on $x$. Thus, one fixed machine can perform any computation described by another Turing machine.

\begin{figure}[htbp]
  \centering
  \includesvg[width=0.7\linewidth]{01 Figures/Universal Turing Machine.svg}
  \caption{A three-tape organization of a universal Turing machine.}
  \label{fig:three-tape-universal-turing-machine}
\end{figure}

In this organization, Tape 1 stores the encoded description of $M$, Tape 2
stores the simulated contents of $M$'s tape, and Tape 3 records $M$'s current
state. The universal machine repeatedly consults the description on Tape 1 and
updates Tapes 2 and 3 exactly as $M$ would, thereby reproducing $M$'s computation
one transition at a time.

The key idea is that a program and ordinary data can both be represented as symbols. A program can therefore be stored, copied, inspected, interpreted, compiled, or generated like other data. This \emph{program-as-data} principle underlies stored-program computers, operating systems, compilers, interpreters, program analyzers, and coding tools.

\section{The Church--Turing Thesis}

Before Turing, people had an intuitive idea of computation: if a task can be
broken into clear, fixed steps, then a trained person can solve it simply by
following those steps. Long division and the Euclidean algorithm are examples.
The person may need time, paper, and practice, but no new creative idea is needed
during the calculation. The important question is whether this intuitive idea
of a mechanical procedure can be captured by one precise mathematical model.

\begin{keyidea}[Church--Turing thesis]
Every function that is effectively computable by an algorithm can be computed by a Turing machine.
\end{keyidea}

The Church--Turing thesis says that this intuitive kind of mechanical
calculation and Turing-machine computation have the same power. If a human can
calculate something by faithfully following finitely described rules, a Turing
machine can carry out an equivalent procedure. Conversely, every Turing-machine
computation is itself a sequence of mechanical steps. The thesis therefore
connects our informal intuition with a formal model and gives us a precise way
to use the word \emph{computable}.

Computability is only about whether some algorithm exists. It does not say that
the algorithm is fast, memory-efficient, or practical. A computation that takes
billions of years is still computable in this sense.

\begin{figure}[htbp]
  \centering
  \includesvg[width=0.6\linewidth]{01 Figures/Computability Boundary.svg}
  \caption{Formal models of computation identify the same boundary between
  computable and uncomputable problems. Before the boundary is formalized, the
  problem universe is not yet classified; the Turing machine makes the division
  precise, and other Turing-complete models recover the same division.}
  \label{fig:computability-boundary}
\end{figure}

\subsection{Why it is called a thesis}

A \emph{thesis} and a scientific \emph{theory} play different roles; they are
not simply earlier and later stages of the same thing. A scientific theory, such
as the Big Bang theory, evolution by natural selection, or the curvature of
spacetime in general relativity, explains empirical phenomena and is evaluated
against observations. The Church--Turing thesis instead connects an informal
human concept---what can be calculated mechanically---with a formal mathematical
model. Evidence can make us highly confident in this connection, but the
connection does not change into an empirical explanatory theory. That is why it
is not expected to ``graduate'' from a thesis into a theory.

\subsection{Support for the thesis}

Strong support for the thesis comes from many independently proposed models of
computation---including lambda calculus, register machines, general-purpose
programming languages, and idealized computers with unbounded memory. Although
these models look different, they can simulate one another and compute the same
class of functions. Many algorithms developed before and after Turing---such as
long division, the Euclidean algorithm, and integer multiplication---also fit
within this class. No accepted example of an effective mechanical procedure has
been shown to compute something beyond it.

This agreement does not prove the thesis from its informal side, but it explains
why the thesis is so widely accepted. Once a problem is known to be computable,
we can then ask the separate question of how efficiently it can be solved.

\subsection{Turing completeness}

A system is called \emph{Turing complete} if it can simulate a universal Turing
machine, assuming that memory and execution time may grow without a fixed bound.
Finite control, expandable memory, and conditional repetition are the essential
ingredients. The term applies the thesis at the level of a computational system:
such a system can express every computation in the Turing-computable class.
Turing completeness describes what the system can compute in principle, not
whether a particular program will halt or run efficiently.

\subsection{What would challenge the thesis?}

A genuine counterexample would be an effective mechanical procedure that
computes a function no Turing machine can compute. Proposed ``hypercomputers''
often depend on assumptions such as exact infinite precision, infinitely many
steps in finite time, or exotic space-time structures. These proposals challenge
what physical processes might be possible rather than providing an accepted
counterexample. Ordinary quantum computers do not overturn the thesis: they may
compute some results more efficiently, but standard quantum computation remains
within the class of Turing-computable functions.

\section{Limits of Computation}

The Church--Turing thesis tells us what counts as mechanical computation. It
does not say that every clearly stated problem can be solved mechanically. We
now move from defining computation to locating its limits. Computable numbers
first give a broad counting argument that such limits must exist; the halting
problem then gives a specific problem and proves directly that no algorithm can
solve it in full generality.

\subsection{Computable numbers}

Turing began with \emph{computable numbers} because producing digits is a
simple, concrete example of computation. To ask whether a number is computable
is to ask whether one finite mechanical procedure can produce as many of its
digits as requested. By modeling an idealized human calculator, Turing made the
informal phrase ``mechanically calculable'' mathematically precise. His point
was broader than decimal expansions: the same machine model can perform any
rule-based symbolic calculation.

A real number is computable if a finite program can generate approximations to
it to any requested precision. Every integer and rational number is computable:
a rational number is specified by a finite numerator and denominator, and
division can produce its decimal digits, including a repeating expansion.
The rational numbers are countable: we can arrange numerator--denominator pairs
on a two-dimensional grid and enumerate the grid as a one-dimensional sequence
of natural numbers, skipping duplicate representations. This is the same basic
idea used earlier to map a two-dimensional sheet of cells onto a one-dimensional
Turing-machine tape.

Some irrational numbers are computable too. For example, the Leibniz series
\[
  \pi=4\left(1-\frac13+\frac15-\frac17+\cdots\right)
\]
provides a rule for approximating $\pi$, although it converges slowly. Other
algorithms can compute its digits much faster. Computability says that a finite
rule exists; it does not promise a practical running time.

There are only countably many finite programs, so there are at most countably
many computable real numbers. The real numbers are uncountable; therefore,
the computable reals form a measure-zero subset of the real line. This is
not a meaningful percentage of all ``real-world problems'': unlike the reals,
that informal collection has no specified measure. The limitation is not that
the tape cannot hold a long output---the tape is unbounded---but that a finite
program cannot specify a digit-generating rule for every arbitrary real number.
Thus, the counting argument proves that noncomputable objects exist, but it
does not yet give a concrete, ordinary-looking decision problem that we can
identify and prove unsolvable. The halting problem supplies that next step.

\subsection{The halting problem}

The halting problem is a decision problem: given a program $P$ and input $x$,
answer \emph{yes} if $P(x)$ eventually halts and \emph{no} if it runs forever.
At first this may seem like a problem that a sufficiently clever analyzer
should solve. We will show, however, that no single algorithm can answer it
correctly for every possible program and input.

The proof uses two ideas that also appear in familiar paradoxes:
\emph{self-reference} and \emph{diagonalization}. The liar sentence---``This
sentence is false''---refers to itself and contradicts either truth value
assigned to it. In the barber paradox, a barber shaves exactly those people who
do not shave themselves; asking whether the barber shaves himself makes either
answer contradict the rule. Self-reference makes an object, rule, or program
act on its own description. Diagonalization focuses on the cases in which each
object is paired with itself and constructs a new case that gives the opposite
answer. The halting proof turns this pattern into a precise argument about
programs rather than a linguistic puzzle.

Suppose, for contradiction, that a universal procedure $H(P,x)$ always decides
correctly whether $P(x)$ halts. Construct a program $D$ that asks $H$ about a
program running on its own description and then deliberately does the opposite
of the prediction:
\begin{center}
\begin{minipage}{0.67\linewidth}
\begin{lstlisting}[language=Python]
def D(P):
    if H(P, P):
        loop_forever()
    else:
        return
\end{lstlisting}
\end{minipage}
\end{center}
Now run $D(D)$. If $H(D,D)$ predicts that this run halts, $D(D)$ loops; if it
predicts that the run loops, $D(D)$ halts. Either answer contradicts the
prediction. This combination of \emph{self-reference} and a reversal of the
predicted behavior is a diagonal argument. Therefore, no such universal
halting decider exists.

\boardplaceholder[4.8cm]{Classroom halting-problem diagram: a hypothetical decider $H(P,x)$ inside a program $D(P)$; $D$ loops when $H(P,P)$ says ``halts'' and returns when it says ``does not halt.'' Feed $D$ its own description to show the contradiction.}

Self-reference alone is not a contradiction: ordinary recursion, such as the
Fibonacci recurrence, also refers to itself. The contradiction arises because
$D$ reverses a prediction about its own behavior. This construction is possible
because programs can be represented as data---the same principle that enables
a universal Turing machine, compiler, or interpreter to process another
program.

\begin{keyidea}[The price of universality]
Universal computers can simulate arbitrary programs, but no universal program can perfectly predict every semantic property of arbitrary programs. Rice's theorem generalizes this limitation: every nontrivial semantic property of the function computed by an arbitrary program is undecidable.
\end{keyidea}

For example, no tool can decide for every possible program whether the function
it computes ever outputs zero. This does not make program analysis useless.
Static analyzers can still find many bugs and security issues by restricting
the programs they analyze or by allowing false alarms and missed cases. Rice's
theorem concerns nontrivial semantic behavior; it does not automatically apply
to every syntactic or resource-usage property.

\subsection{Computation, cognition, and consciousness}

The lesson is that questions about computational limits must first be stated
precisely. \emph{Computability} asks whether a task can be carried out by a
mechanical procedure. To study a task in this way, we must specify its inputs,
required outputs, and the conditions under which an answer is correct.

Many \emph{cognitive} abilities can be described as information-processing
tasks. Calculating, recognizing patterns, remembering, planning, and using
language can therefore be studied with computational models. This does not
establish that every aspect of human cognition is computable, but it allows us
to ask precise questions about representations, procedures, and observable
behavior.

\emph{Consciousness} raises a different question. It concerns subjective
experience: what seeing a color, feeling pain, or being aware feels like from
the inside. A system may reproduce the observable input--output behavior of a
cognitive task, but that achievement alone does not tell us whether the system
has subjective experience. Computability concerns what a procedure can do;
consciousness concerns what, if anything, the process feels like.

The Church--Turing thesis characterizes mechanical computation, and
undecidability results identify limits on what algorithms can determine.
Neither claim establishes that the human mind is entirely computational, and
neither shows that consciousness lies beyond computation. Those broader
questions require both clearer concepts and empirical investigation.

\section{Stored-Program Computers}

In a stored-program computer, memory contains both instructions and data. A CPU repeatedly performs a fetch--decode--execute cycle:
\begin{enumerate}
  \item fetch the instruction whose address is in the program counter;
  \item decode the instruction;
  \item execute it and update registers or memory;
  \item update the program counter.
\end{enumerate}
Conditional branches and jumps change the program counter, making selection and repetition possible.

The von Neumann architecture is a prominent organization of this idea: a processor communicates with a shared memory that stores both code and data. It is a practical architecture, while a Turing machine is a mathematical model. Both embody finite control operating on expandable memory.

\section{Complexity: The Cost of Computation}

Computability asks whether some algorithm exists. Complexity asks how resources grow with input size. The most common resources are running time and memory.

\subsection{Input size and asymptotic growth}

For an integer, input size usually means the number of digits or bits, not the integer's numerical value. If a decimal integer has $n$ digits, a digit-by-digit algorithm naturally performs work as a function of $n$.

Big-$O$ notation describes an asymptotic upper bound. It suppresses constant factors, lower-order terms, exact processor speed, and behavior on small inputs. Common growth rates include
\[
 O(1),\quad O(\log n),\quad O(n),\quad O(n\log n),\quad
 O(n^2),\quad O(2^n).
\]
For sufficiently large $n$, the shape of the growth function matters more than small constant differences.

\subsection{Searching an attendance list}

Finding a name in an unsorted list by checking entries in order takes $O(n)$ time. If the list is sorted, binary search takes $O(\log n)$ comparisons: about $7$ comparisons for roughly $100$ entries and about $30$ for one billion entries. A hash table can provide $O(1)$ expected lookup time by using additional memory and preprocessing.

This example illustrates a recurring time--space tradeoff: a method may run faster because it stores a more helpful representation of the data.

\subsection{P and NP}

\begin{definition}[P and NP]
\textbf{P} is the class of decision problems solvable in polynomial time. \textbf{NP} is the class of decision problems for which a proposed yes-certificate can be verified in polynomial time.
\end{definition}

Every problem in P is in NP because a problem that can be solved efficiently can also have its answer verified efficiently. Whether every NP problem is also in P remains unknown:
\[
  \mathrm{P}\stackrel{?}{=}\mathrm{NP}.
\]

Subset Sum illustrates the distinction. Given integers and a target, the decision problem asks whether some subset sums to the target. A proposed subset is easy to check, but naive search examines as many as $2^n$ subsets. This does not prove that the problem lacks a polynomial-time algorithm; it explains why verification may appear much easier than discovery.

\section{Hierarchical Abstraction}

The Turing machine tells us what a mechanical computer can compute. Computer architecture explains how a physical machine executes instructions. Abstraction explains how people build usable systems on top of that machinery.

\begin{definition}[Abstraction and interface]
An \emph{abstraction} hides details that are unnecessary for the current task. An \emph{interface} specifies what a component makes available to its users without requiring them to know its internal implementation.
\end{definition}

When writing \texttt{2 + 3} in Python, a programmer does not need to reason about transistors. The operation passes through layers such as language semantics, interpreter or compiler, machine instructions, digital circuits, logic gates, transistors, and electrical behavior. Each layer exposes a simpler interface to the layer above it.

Likewise, clicking \emph{Send} in a messaging application may involve the application interface, operating-system services, network protocols, device drivers, hardware, and physical signals. No single application developer needs to rebuild all of these layers.

\subsection{Leaky abstractions}

An abstraction leaks when lower-level details affect behavior visible at a higher level. Examples include:
\begin{itemize}
  \item a Python list appears able to grow, but physical memory remains finite;
  \item a network request resembles a function call, but latency and failure remain possible;
  \item a file appears to be a stable sequence of bytes, but storage devices can fail;
  \item two algorithms implement the same function, but their running times may differ dramatically.
\end{itemize}
Abstraction does not erase lower layers. It allows us to ignore them until performance, correctness, security, or failure forces us to cross an interface and inspect the implementation.
